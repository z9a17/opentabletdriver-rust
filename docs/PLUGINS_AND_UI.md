# Control panel and plugins

Extract the complete Windows release ZIP and open **opentabletdriver-rust-ui.exe**. The control panel follows OpenTabletDriver's desktop layout: a **File / Tablets / Plugins / View / Help** menu bar, **Output**, **Filters**, **Pen Settings** and **Console** tabs, and a bottom bar with the tablet status, **Save** and **Apply**. The console executable retains its existing no-argument foreground behavior; `opentabletdriver-rust.exe ui` also opens the panel.

- **Output** draws the display area over your monitors and the tablet area over the PTH-660's 224 × 148 mm surface, as upstream's area editors do. Drag an area, type its size, center and tablet rotation, or right-click it for alignment, resizing, flipping, **Set to display**, **Lock to usable area**, **Lock aspect ratio**, **Clamp input outside area** (clipping) and **Ignore input outside area** (area limiting). The dropdown below the editors switches between **Absolute Mode** and **Relative Mode** (X/Y sensitivity, rotation and reset time).
- **Filters** lists the built-in Radial Follow port and the profile's native and .NET plugin entries. Each has an **Enable** check box and its settings.
- **Pen Settings** sets the tip and eraser bindings (left click or none) and their activation thresholds in percent. An empty threshold uses the pen's own tip switch.
- **Console** lists driver, settings and plugin messages with their time and level. When a device session ends it also shows how long reports took from read to output; see [input latency](INPUT_LATENCY.md). **Copy All**, or Ctrl+C on selected rows, copies them.

The panel follows the Windows light or dark app mode and switches when it changes. **View > Theme** picks Light or Dark instead; high-contrast themes use the system colors. The theme, the area locks, the window size and the **Start driver when the panel opens** setting are stored in `ui.toml` beside the profile, never in the profile itself.

The panel opens `driver.toml` from `%LOCALAPPDATA%\OpenTabletDriverRust` (or the absolute `OTD_RUST_PORTABLE_DIR`), otherwise imports OpenTabletDriver settings. It connects to an existing daemon in the background and fetches the active profile without replacing unsaved edits. The launch preference can start an idle daemon without a console window; **Tablets > Start driver when the panel opens** disables automatic start. Once this panel has observed an active worker, queued autostart cannot revive it after another client stops it. **Start driver** connects or starts explicitly. **Apply** (Ctrl+Enter) and **Save** request a replacement guarded by daemon instance and worker generation. The daemon prepares it while current input continues, then quiesces and activates; pre-commit activation failure can resume the retained previous worker. See [runtime reconfiguration](RUNTIME_RECONFIGURATION.md) for state, cleanup and rollback limits. Closing the panel requests a guarded stop, waits for the worker to finish in the background and then closes. Minimizing keeps input running. An unconfirmed stop leaves the panel open with an error. CLI `shutdown` stops the service after cleanup. A protocol-v1 service is left untouched and blocks automatic launch; stop/shut it down using its original executable before migrating. Errors appear in the Console.

**Tablets > Tablet debugger** polls the daemon about 30 times a second with the `debug` control command. While it polls, the report thread copies each packet into one fixed slot, skipping a packet rather than waiting if the slot is busy. When nothing polls for about 2,000 packets the copy stops, and the report thread then does one atomic load per packet. The daemon returns the latest packet undecoded; the panel (or the `debug` command) decodes it in its own process with the session's parser, so a decoding fault cannot stop the driver. A fresh parser decodes each snapshot, so stateful parsers show only what one packet carries. **Tablets > Settings for tablet** lists the connected supported tablets and saves the choice as `tablet = "Name"` in the profile. A profile without it runs on whichever supported tablet is connected. Choosing a tablet keeps the tablet area inside that tablet and caps pressure thresholds at its range.

**Plugin manager.** The manager follows the panel palette, including dark and high-contrast modes. It downloads OpenTabletDriver's Plugin-Repository catalog and shows each plugin's newest version that declares support for OpenTabletDriver 0.6.7. Installing works as follows:
- the download must match the catalog's SHA-256, and a plugin without a declared hash is refused;
- the archive is extracted to `%LOCALAPPDATA%\OpenTabletDriverRust\Plugins\<name>`, with a copy of its metadata;
- an installed version is renamed aside first and restored if installation fails.

**Add to settings** inspects the plugin's DLLs, running their code as **Add .NET plugin** does, and adds every exported position filter. Plugins that only provide bindings, tools or output modes install but add nothing, because the driver cannot run those yet. **Remove** deletes the folder. A plugin loaded by the running driver can't be removed until the driver stops.

**Downloads.** The catalog, plugins and updates download with Windows' `curl.exe`, through the proxy the Windows proxy settings give each address: automatic detection, a setup script, or the manual proxy and its exceptions. Redirects are followed one request at a time, because GitHub serves release files from a different host than its pages and API. As in OpenTabletDriver's .NET downloads, certificate revocation is not checked, so an unreachable revocation server cannot block a download; certificates and host names are still verified, and plugins and updates must match their SHA-256. A failed download names the host, the proxy if one was used, and curl's reason.

**Updates.** The panel checks the latest GitHub release when it opens (Help menu toggle) and on **Help > Check for updates**. A launch check that finds a release while the panel is not in front shows a tray notification and waits for the panel to be activated instead of taking focus. Installing:
1. `curl.exe` downloads the release ZIP and its SHA-256 file.
2. Windows CNG verifies the hash, and `tar.exe` extracts the ZIP.
3. Every installed file is renamed aside before its replacement is copied, so running executables and loaded DLLs keep working. If any step fails, every file is restored.
4. **Restart** stops the daemon, starts the new panel and closes the old one.

The renamed files are removed at the next start. For a private repository the updater needs `GH_TOKEN`, `GITHUB_TOKEN` or a logged-in GitHub CLI. It passes the token to curl in a temporary header file, sends it only to GitHub's API and not to the storage host a download redirects to, and deletes the file afterwards.

**Startup and presets.** **Tablets > Start with Windows** writes one `OpenTabletDriverRust` value under the current user's `Run` key, and turning it off removes only that value. The value opens the panel with `ui --tray`. **File > Presets** lists the presets in `%LOCALAPPDATA%\OpenTabletDriverRust\presets`. Choosing one loads it as unsaved settings. **Save settings as preset** saves in that folder and asks before replacing a preset.

As in OpenTabletDriver, the panel keeps an icon in the notification area while it runs. Minimizing the panel hides it there and removes its taskbar button; clicking the icon, or **Show Window** in its menu, brings the panel back. The icon's tooltip shows the driver state. Its menu also has **Start driver** for recovery and **Close**, which stops tablet input before closing the panel. Opening the panel again while it runs brings the running panel forward instead of starting a second one. A shortcut set to run minimized starts the panel in the tray.

Profiles that use the older crop/monitor keys appear as the equivalent areas; the file keeps that form until you edit an area. `device_path` has no editor and is preserved.

**Save** stages and flushes the profile, retains the previous file in its reserved `.bak` sidecar and checks that the destination still matches the bytes originally loaded. External edits require Reload or Save As. The destination revision continues increasing even when an older daemon configuration replaces a clean editor. **Save settings as...** requires a new file name. **File > Recover backup as unsaved settings...** validates the backup and loads a dirty editor; a failed Load also offers recovery when a backup exists. Recovered settings require Save As to a new path, preserving both primary and backup. Recovery alone does not apply settings. See [persistence limits](parity/BEHAVIOR_CONTRACTS.md#profile-persistence).

## Existing OpenTabletDriver .NET plugins

Use **Plugins > Add .NET plugin...**, or **Add .NET...** on the Filters tab, to select an unchanged plugin assembly. Its exported OTD filter classes are added as disabled entries. Select a class, edit its settings, then check **Enable**. The Filters tab reads `[PluginName]`, `[Property]` display names, `[Unit]` and `[ToolTip]` from the DLL, including for entries loaded from a saved profile. The editor shows every declared property, including omitted settings, with boolean/enum choices, supported scalar type checks and default information on hover. Flags keep text editing; long lists have Previous/Next pages. Per-property default buttons and the raw JSON editor are removed. Unknown and structured values remain preserved, with unsupported settings read-only. Invalid edits block Save/Apply. The selected-filter **Defaults** action remains, and matching Save/Apply replies keep the filter selection and page. Viewing an omitted property does not materialize it or construct a plugin. Metadata is cached in memory; saved profiles now use schema 1. At load time, a missing property keeps its constructor value. An explicit JSON `null` selects `[DefaultPropertyValue]` when present and otherwise keeps the constructor value; settings are applied before `[OnDependencyLoad]`. The plugin's adjacent dependencies must remain alongside its DLL. Add only trusted plugins: both native and managed DLLs execute with the driver's permissions.

Discovery omits filter classes marked `[PluginIgnore]` or restricted to another OS by `[SupportedPlatform]`. If a saved profile enables such a class explicitly, loading reports why it was rejected; no other filter is substituted. This follows upstream's [platform and ignore checks](https://github.com/OpenTabletDriver/OpenTabletDriver/blob/736003ed72c8bbb28033b039d5a0bb76c344145c/OpenTabletDriver.Desktop/Reflection/DesktopPluginManager.cs) and [platform flag contract](https://github.com/OpenTabletDriver/OpenTabletDriver/blob/736003ed72c8bbb28033b039d5a0bb76c344145c/OpenTabletDriver.Plugin/Attributes/SupportedPlatformAttribute.cs).

The bridge supports **synchronous zero/one/multiple-emission filters** implementing OpenTabletDriver's `IPositionedPipelineElement<IDeviceReport>`. PreTransform filters run on tablet coordinates before mapping. Pixels/PostTransform filters run after mapping, on desktop pixels in Absolute Mode and motion deltas in Relative Mode. The bridge uses the official `OpenTabletDriver.Plugin` **0.6.7** assembly, sets `[Property]` values/defaults, injects a `[TabletReference]` from the Rust-selected pinned tablet configuration, and invokes `[OnDependencyLoad]` methods. The driver selects a supported PTH-660 configuration and matching identifier; overrides that change its parser, report length or specifications beyond runtime support are rejected. Earlier releases passed integration tests for the original, unchanged **RadialFollow 0.3.0 DLL** tablet-space and screen-space classes. The managed emission graph added in 0.9.0 has compiled but has no new plugin integration or hardware evidence. Select either class in the panel's Filters tab; screen-space radius settings are in pixels.

Compatibility is deliberately explicit:

- Supported managed filters may emit zero, one or several reports synchronously on the owning thread. Each Emit immediately traverses downstream nodes with the same managed object, retaining its concrete type and mutations; there is no output collection/replay step. The host projects supported capabilities into bounded native values at transform/output boundaries. Post-filter pressure/eraser values feed the existing tip contact policy. Broader button/auxiliary bindings remain unimplemented. Native DLL ABI v1 remains position-only and PreTransform-only.
- Pixel/PostTransform filters can run in either output mode, subject to their own coordinate assumptions. Timer-driven (async) filters run: their `ITimer` ticks on the report thread and emissions continue down the pipeline. Tools start and stop with the driver. Output-mode plugins (including Windows Ink), bindings, and filters requiring other unresolved services are not supported. They fail initialization or are disabled if they violate the synchronous contract. DLL discovery lists available filter classes; discovery does not guarantee each class is supported.
- The report adapter supplies position, pressure, eraser, actual raw bytes, pen buttons, tilt and proximity when present in the source report. Imported reports own their arrays so retained references remain stable; the same object continues through managed nodes. Managed allocations remain, and current performance evidence is pending. Device-specific input concrete types are not emulated, and rotation remains in raw bytes. The graph accepts at most 32 enabled nodes; capability limits and nonfinite values are checked explicitly.
- Unsupported enabled filters in imported OTD settings remain archived with explicit diagnostics and are not run. Add their DLL/type/settings explicitly in the panel. **Plugins > Plugin manager** installs catalog plugins; automatic settings migration is not implemented yet.
- The existing native Radial Follow port remains the efficient default for imported profiles. To use the original .NET Radial Follow instead, uncheck the built-in entry on the Filters tab (this removes its `[[radial_follow]]` block) before enabling the DLL, so smoothing is not applied twice. The panel warns while both are enabled, and execution validation rejects that duplicate smoothing configuration.

Keep the release's **compat/** folder beside both executables and install the **Windows x64 .NET 8 runtime or newer**. The bridge is framework-dependent; it does not download or install a runtime. Rust-only/native-plugin profiles do not start .NET. Hosts with no .NET runtime can still use the native UI, Rust built-ins, and native plugins.

Diagnostic commands, which do not open HID or inject input:

```text
opentabletdriver-rust.exe inspect-plugin C:/plugins/RadialFollow.dll
opentabletdriver-rust.exe check-plugins driver.toml
```

These commands load executable plugin code. Plain `settings` validates configuration without loading DLLs. `inspect-plugin` prints class names/default properties; `check-plugins` checks all enabled plugins and reports initialization errors.

New imports honor disabled Radial Follow entries. Older saved native `[[radial_follow]]` entries stay active when loaded; an explicit legacy import option is available for restoring the earlier force-enable behavior during migration. Schema-1 profiles preserve the full original OTD source text and archive unsupported native fields. Preservation and export do not imply runtime support for every stored plugin or binding.

The GUI and CLI share the persistent daemon through protocol v2. Pipe calls run on a background client with bounded queues; status messages use sequence numbers to avoid repeated log replay. See the [headless commands](../README.md#profiles-and-headless-control).


Version 0.14.1 shows declared defaults in property help and filter-row hover summaries. Installing or updating a package discovers its supported filters and tools in the background; new entries are disabled until enabled and applied. Discovery merges DLL/type identities instead of adding another copy, preserving existing settings and order. Attribute and slider defaults seed new entries. Constructor-only defaults remain unknown during inspection: imported omitted values keep constructor semantics, and inspection never constructs a plugin just to read a default. DateTime and TimeSpan fields accept literal text. Plugin information refreshes after updates and removals without discarding an active or invalid draft.

## Native Rust plugins

The release also includes `otd_ema_filter.dll`, a small exponential-smoothing example. [driver.plugins.example.toml](../driver.plugins.example.toml) enables it. Its `alpha` is in 0..1 (1 follows the pen immediately) and `reset_ms` sets the inactivity reset. Relative DLL paths resolve against the profile's directory, not the process's working directory. In the panel, **Add native...** adds a DLL entry; its settings are edited as JSON because native DLLs do not describe their properties.

The versioned C ABI is defined in [otd-plugin-api](../crates/otd-plugin-api/src/lib.rs); the buildable example is in [plugins/ema](../plugins/ema). Plugins export `otd_filter_v1`, returning a version/size-checked table with a fixed-size name and create/process/reset/destroy callbacks. JSON is decoded only on creation. A context is owned and freed by its DLL; Rust-owned allocations never cross the boundary. Callbacks run in report order on one driver thread. They must not unwind, block, retain sample pointers, or allocate per report.

The pipeline runs built-in Radial Follow first, then PreTransform DLL entries in profile order, then mapping, then Pixels/PostTransform DLL entries in profile order before mouse output. A native ABI callback failure disables that plugin and preserves the prior valid position. A managed graph failure stops the current dispatch without replaying already emitted output, disables the identified failing node where possible, and requests held-output cleanup before dispatch can resume. Losing the pen (neither hover bit set) or reconnecting resets healthy plugin instances; restart the driver to retry a disabled plugin. Native ABI version 1 filters position only.

## Efficiency and verification

Native callbacks use fixed-size samples and function pointers. The .NET bridge hosts CoreCLR in-process using Microsoft's `nethost`/`hostfxr` interfaces, with owned input snapshots, plugin handles and a direct synchronous emission graph. There is no per-report JSON, reflection, subprocess IPC, or report queue. Driver reflection, configuration, DLL loading and dependency resolution happen at startup; UI metadata inspection happens when the Filters tab opens. Third-party managed plugins can still allocate or pause for GC; Rust-only measurements do not characterize .NET plugin latency. The daemon owns the report worker; GUI polling/control and serialization run in a separate client thread, never on the report thread or UI message loop. The panel renders at the monitor's DPI; mapping uses the daemon's display snapshot.

Historical checks below describe earlier builds; they do not validate the 0.9.0 graph/daemon UI/persistence changes or the 0.10.0 runtime transaction, converters, presets and decoders. No local tests, plugin execution, GUI or hardware runs were performed for this increment. Rust formatting and strict workspace/all-target Clippy passed for 0.10.0 integration; the prior C# bridge compilation result belongs to 0.9.0 until packaging records a new result. Final packaging results are recorded in the release notes.

The native DLL integration test loads the compiled sample, verifies its smoothing and reset, and checks the Rust-side report call for allocations. The .NET integration test loads the unmodified upstream RadialFollow DLL, checks tablet and screen dead zones, verifies labels/units/tooltips, and replays the screen class through mapping and a simulated mouse output. Its archive is checksum-pinned in CI. A mixed-stage native test checks ordering and no Rust allocation during a report. Profile serialization/mapping tests cover UI saves and fractional output from simple TOML profiles. Unit tests cover the panel's editing model: area locks, alignment and flips, crop-to-area conversion, threshold percentages, output-mode switching and plugin settings. The window itself has no automated test. Earlier releases were checked with scripted runs against sandboxed profiles: every tab in both themes, field edits and validation, area dragging, context and dropdown menus, OpenTabletDriver import, saving, and Start/Apply/Stop with a device path that does not exist. The metadata display added in 0.7.4 has not had a visual window check. Live pen feel, successful device start/stop and plugin behavior across hardware reconnects remain manual checks.

Build and package on Windows with Rust stable and a .NET 8+ SDK:

```powershell
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
pwsh -File scripts/package.ps1
```

The package script builds both executables, the sample DLL, the compatibility bridge and notices, then produces a versioned ZIP and SHA-256 sidecar in `target/`.
